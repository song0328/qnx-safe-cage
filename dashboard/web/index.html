When AI code fails, QNX keeps the safety layer working

Same VM, same controller code. Each test switches off one QNX mechanism and compares. Medians of 3-5 runs; full tables in results/exp/REPORT.md.

The AI code crashes
Separate process (QNX)0.02 s
Same process5.0 s

In one process the safety layer dies with the AI code and the drive runs unguarded. Same for infinite loops, memory leaks and CPU hogs (5.0-6.4 s, 3/3 each).

The AI code rewrites the safety limits
Separate process (QNX)85 °/s
Same process133 °/s

In one process the limits were found in memory and raised: the arm ran at 133 °/s against a 90 °/s limit while the safety layer reported PASSED (3/3).

Another app keeps the CPU busy
Safety layer at priority 7044 ms
At an ordinary priority (10)8.0 s

At an ordinary priority one busy app at priority 30 or 63 froze the safety layer for the whole 8 s load (15/15). Shown: worst tick delay.

What we did not prove

  • All timing is from a VirtualBox VM; real hardware is next.
  • One red-team replay touched 100.0 °/s for 2 ms when a governor tick came 8 ms late. A speed limit in the drive itself is the missing layer.
  • The fixed-priority channel flag showed no measurable effect (40 runs). No Linux comparison yet.
